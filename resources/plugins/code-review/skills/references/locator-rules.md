# 代码定位（Locator）规则

代码审查的每条 problem 必须落在**稳定、可复核的代码位置**上，供代码视图面板定位、
标记与导出。锚定文件、函数、行号，并附可全字匹配的问题代码语句。

## 1. 定位字段

每条 problem 至少包含：

- **`file_name`**（必填）：相对项目根目录的路径，正斜杠分隔。例：`src/core/route/nav.c`。
- **`function_name`**（可选）：所属函数名。
- **`issue_location`**（必填）：`文件路径:函数名`，如 `src/core/route/nav.c:distance_km`。
- **`description_location`**（必填）：**必须严格按以下格式**：
  ```
  xx文件的xx函数的xx行：问题代码语句源程序为：
  \n保留关键上下文的源程序代码
  ```
  - 示例：`src/core/route/nav.c文件的distance_km函数的23行：dlat = (lat2 - lat1) * DEG_TO_RAD;源程序为：\ndouble distance_km(...) {\n    ...\n    dlat = (lat2 - lat1) * DEG_TO_RAD;\n    ...\n}`
  - **问题代码语句是最关键的定位信息**，必须写在 `源程序为：` 之前（冒号后紧跟）。
    前端将用该语句在源码中做**全字匹配**定位并高亮该行。
  - `源程序为：` 之后必须**原样保留**关键有问题部分及其必要上下文的源代码；无关部分
    可以用 `......` 省略，但问题代码语句及其必要上下文必须保持源码原样（去多余空格、
    保持原始语法）。
  - 在 JSON 字符串中，`description_location` 内的换行必须用 `\n` 转义，不要用未转义的真实换行。

## 2. 稳定性规则

- **同一缺陷只用同一个 `id`**：重复审查同一函数/链路时，回到同一个 `id`，不新建。
  这样面板里的"已查看/已过滤/已标记"状态才能跨次复用。
- **定位到代码语句，不定位到描述**：问题代码语句是位置，问题表述放 `issue_name` /
  `description_issue`。
- **跨文件关联用 `related`**：链路/功能审查关联其他函数/文件时，在 `related` 中放
  对方 `issue_location`（格式 `文件:函数`），不要塞进本条 `description_location`。

## 3. 引用证据

- `evidence`（可选）：判断依据——引用的调用点、条件、宏、或索引库中的调用边。
  例如 `route_ok:30 调用 distance_km`。证据来自代码本身或索引结果，不得编造行号。
- 复用索引工具拿到的真实符号与调用边（`get_call_graph` / `get_function`），不要靠
  记忆或猜测行号。

## 4. 外部符号

- 调用图里 `callee_id: null` 的调用（如 `sin`、`cos`、系统库）只作关联背景，不作为
  缺陷本身，除非其错误处理缺失构成缺陷。

## 5. 干净时

- 未发现问题时输出空 `problems` 数组，不制造问题以求全面。
