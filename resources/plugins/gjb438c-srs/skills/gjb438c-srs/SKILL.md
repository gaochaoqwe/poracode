## 二、工作流（严格分阶段，未获用户确认不得进入下一阶段）

### 阶段一 · 提炼清单

#### 材料来源与用法（先分清每份材料负责什么）

用户可能给**三类**材料，缺哪类就用有的哪类；**没有代码和参考文件时，自行规划结构与顺序并说明**。

- **研制任务书 / 系统需求（必给）**：告诉你**有哪些需求**——功能/能力清单、外部与内部接口、性能与质量要求的**名称与边界**。它是需求的**来源**。
- **参考源码（给了就必须读）**：告诉你需求的**细节**——具体参数、接口字段与取值、实现差异、异常与边界条件。启动场景会给出**源码目录**与用户声明的**库/第三方目录**：
  - **先实际打开并阅读**目录下的手写源码（用文件工具逐文件读，**不要只凭路径臆测**）；**大目录按模块分批读**；
  - **跳过**用户声明的库/第三方目录，**不对其中的代码写任何需求**；
  - 每条从代码得出的细节，**记下它来自哪个文件/函数**，供用户核对。
  - 代码与研制任务书冲突时：以任务书定"有没有这条需求"，以代码定"这条需求的参数与实现细节"，冲突处标出来问用户。
- **同型号相似需求（可选）**：只提供**排列顺序与书写习惯**（章节组织、条目写法、措辞），**不得**当作需求来源，也不要直接照搬——它与本项目不完全一样。

- 通读用户提供的材料（研制任务书 / 系统需求 / 任务书 / 接口文件）。**材料很大时按章节标题分批读取，不要把全文一次读入**——只取与本章需求相关的部分。
- 把材料提炼成一份**结构化清单**，写入 `<项目根>/.agentemployee/gjb438c-srs/requirements-digest.md`，至少覆盖：
  - 软件识别信息（名称、简称、版本、开发单位等）；
  - 要求的状态与方式（对应 3.1）；
  - **功能（能力）清单**（对应 3.2）；
  - **外部接口清单**（对应 3.3）与内部接口（3.4）；
  - 数据、性能、质量、安全、保密、环境、资源、人员、培训等需求要点；
  - **材料中缺失或存疑的点**（明确标出，供用户补充）。
- **此后所有填写都基于这份清单**，不要反复通读原文；只有材料变动时才回读对应片段。
- 向用户确认清单无误，尤其让用户补齐「缺失/存疑」项。**不要臆造**。

**配图清单（SRS 默认；阶段一与用户确认后执行）**

图放在**对应章节标题后的第一段**（标题后紧跟图），图**下方**配题注 `图<章>-<序> <标题>`（编号由 `insert_image.py` 自动续）：

| 锚点（**模板里真实存在的**段落文字） | 图                                                           | `render_diagram.py --kind` |
| ------------------------------------ | ------------------------------------------------------------ | -------------------------- |

| 接口标识和接口图（3.3 内的一段文字） | 接口交联关系图                                               | `blockdiag` 或 `nwdiag`    |

- **锚点用上面这些真实文字**（模板里**没有** `3.3.1` 这种小节号段）；同一节多张图按插入顺序堆叠。要挂到更细的小节下，先在正文里写出该小标题行再以它为锚点。

### 阶段二 · 条目大纲确认（必须逐条列全，然后停下等待确认）

基于清单输出**需求条目大纲**，并且**必须显式列出**（不能只说"将生成若干条"）：

- **3.1 要求的状态和方式**：有哪些状态/方式（每个 `3.1.x` 的正文按 `a) 状态（方式）说明 / b) 需求条目` 写，见第四节）；
- **3.2 软件能力需求 —— 功能划分**：逐条给出 `3.2.1 <功能名>`、`3.2.2 <功能名>`…，每条一句话职责（数量与命名由你依据材料判断，建议 3–8 个）；**若某条下含两个及以上职责明显不同的子功能，同时列出 `3.2.1.1 <子功能名>`… 并说明拆的理由**；
- **3.3 软件外部接口需求 —— 接口划分**：逐条给出 `3.3.1 <接口名>`、`3.3.2 <接口名>`…，每条一句话说明连接实体与用途；子接口同理可拆 `3.3.1.1`…；
- **3.4 软件内部接口需求** 及其后 3.5–3.18 各条的要点（可概述，但不得留空不提）；
- 每个 `3.2.x / 3.3.x` 的正文将按 **a)–g) 字段**写（见第四节），大纲阶段只需确认**能力/接口清单与层级（是否拆子能力）**。

输出后**停下，等用户确认或修改**。用户未确认前：不要填写正文、不要建工作副本、不要运行引擎。

## 四、JSON 规则

**config.json**：分 `project`、`document`、`content` 三部分，只修改各字段的 `content` 值，不动 `type`、`replacement_pattern` 等结构字段。

**project.json**：

- 只修改 `content`、`subsections` 与 `rows`；不改 `id`、`name`、`type`、`columns`、`replacement_pattern`、`locator_rows` 等模板结构字段。
- 第 1 章（范围）用 `placeholders`；第 2 章（引用文档）用 `tables`；第 3 章（需求）用 `placeholders`（含 `subsections` 动态章节与 `tables` 合格性/追踪表）；第 4 章（合格性规定）用 `tables`；第 5 章（需求可追踪性）用 `tables`；第 6 章（注释）为静态章节。
- `subsections` 的键必须是有效章节编号（如 `"3.2.1"`）；**允许四位编号**（`"3.2.1.1"`）表示子能力，引擎按编号排序并各自生成小标题。
- `rows` 中每行的字段必须严格等于 `columns` 定义。
- `locator_rows` 必须与模板中的实际表头文本完全一致。

### 3.1 / 3.2 / 3.3 正文格式（`subsections["3.x.y"].content` 必须逐行照写）

引擎只把 `content` **按行**复制成段落，**不会**自动加字段名或编号——所以 `a) b) …`、`1) 2) …` **必须由你写成正文行**。任一字段下**有多条**都用 `1) 2) 3)` 划分（只有一条时可单行、不编号）；字段没有内容写「无」，**不要留空**。

**3.1 要求的状态和方式**（每个 `3.1.x`）：

```
a) 状态（方式）说明：<该状态/方式的定义与行为>
b) 需求条目：
1) <需求编号> <名称>：<需求正文>
2) <需求编号> <名称>：<需求正文>
```

**3.2 软件能力需求**（每个 `3.2.x`，**严格按 a–g 次序**，缺项写「无」）：

```
a) 标识号：<本能力的标识/编号前缀>
b) 说明：<能力职责与行为>
c) 输入：<…>
d) 输出：<…>
e) 处理：
1) …
2) …
f) 性能：<指标；未定的写"待确认">
g) 约束条件：<…>
```

**3.3 软件外部接口需求**的每个 `3.3.x` 用**同一套 a–g**，语义换成接口：标识号 / 说明 / 输入 / 输出 / 处理 / 性能 / 约束条件。

**子能力拆分**：当某个 `3.2.x`（或 `3.3.x`）下含**两个及以上职责明显不同、各自需要独立需求条目**的子功能时，拆成 `3.2.1.1`、`3.2.1.2`…——在**同一个 `subsections` 映射**里加四位编号的键（引擎按编号排序并各自生成小标题），`name` 为子能力名，`content` 用同一套 a–g 模板；此时 `3.2.1` 自身的 `content` 只写一句总述（如「本能力包含 3.2.1.1–3.2.1.n。」）。**职责单一、无独立条目的不要拆。**
