### 编写原则（贯穿全程，先读这条）

1. **三类变更互斥、不得重复**：每一项变更只归入 **3.1 需求变更 / 3.2 设计变更 / 3.3 代码变更** 中的**一类**，并且**只写一次**。若某项变更本质上是需求变更，就不要在代码变更章节再登记一遍；同一变更在其他章节只以"影响"形式出现（例如需求变更对编码的影响写在 `3.1.x.3 对关联编码的影响`），**不再单列一个子节**。三章内不得出现同名或同一变更的两个条目。
2. **关联变更合并为一条**：先分析多项变更之间的关联——同一次修改引起的连锁改动、同一缺陷的多种表现、成组的新增/修改/删除——把**能够关联到一起的合并为一个变更项（一个小节）**，在该小节内统一描述其依据、标识号、说明、性能指标与限制约束，以及它的各项影响。**不要**把一个关联变更组拆成多条并列子节。
3. **先大纲、后正文**：必须先产出并确认"变更项大纲"（阶段二），用户确认后才写报告正文（阶段三）。未确认大纲前，禁止填写正文、建工作副本、运行引擎。

### 阶段一 · 提炼清单

#### 材料来源与用法（先分清每份材料负责什么）

本场景**必给两份代码材料**（另可附**参考文档**，可选），缺必需的向用户索要：

- **变更前版本代码（必给）**：变更的基线。用于确认"变更前是什么样"——原有需求、设计、接口与实现。
- **当前版本代码（必给）**：变更后的实现。用于确认"变更成了什么样"。
- **参考文档（可选）**：联试纪要、缺陷报告、变更申请单、任务书、需求规格说明、设计说明等，用于界定**变更意图与原因**。**只认用户在上传区给出的参考文档**：给了就**优先采信**，用来确认某处改动"为什么改""是不是同一批变更"；没给就仅依据两版代码差异推断，并明确说明推断依据。
- **没有参考文档时：只看两版代码，不得去工程里乱找文件**：**不要**在工程目录（工作目录、`docs/`、根目录等）里翻找别的文件当参考（如 `rizhi.md`、任务书/需求/设计文档、截图、README、旧报告、已生成的产物等）——它们**不在本次输入里**，可能与本变更无关，拿来当参考会污染结论。**只有用户明确指定的文件才可以读**。缺依据时把该项标为"待确认"并向用户追问，**不要**拿无关文件凑数。
- **先用 `diff_paths` 工具对比两个代码目录**（本场景的核心步骤）：调用 app-controls 的 `diff_paths`，入参 `projectId` + 两个**项目内相对路径**（变更前目录、当前目录），内部走 `git diff --no-index`，返回**变更文件清单 `changedFiles`（path + 增删行数）+ unified diff**。工程带版本历史时也可配合 `git_status` / `git_diff`。**不要**自己写脚本或依赖 `diff` 命令。
  - **必须传 `excludePaths`**：把用户在外层「库/第三方目录」里声明的目录、以及明显的**构建产物目录**（如 `build-base`、`build-debug`、`build-*`、`out`、`dist`、`node_modules`）作为 `excludePaths` 传进去（路径**相对各对比根**）。否则 diff 会被 `.obj/.exe/CMakeCache` 之类淹没——结果有 80k 字符截断，前面的构建产物会把真正的源码差异全部挤掉，agent 根本看不到代码改动。先看 `list_project_files` 确认两版目录下有哪些构建/产物目录，再排除它们。
  - **大差异要分两步取**（patch 上限 80k 字符）：`changedFiles` **始终完整返回，不受截断影响**，所以先看它拿到"改了哪些文件 + 各改多少行"；需要看具体改动时，再带 `filePaths: ["<子目录或文件>", …]` **只拉指定范围的 patch**（`statOnly: true` 可只取清单、跳过 patch）。**不要**指望一次拿到整个大 diff——80k 会把后面的文件悄悄截掉。
- **再按需回读源码**：diff 只给"变了什么"，细节（参数、接口、异常分支）要**实际打开并阅读**对应源码确认（用 `read_project_file` / `list_project_files` / `find_files`；**大目录按模块分批读**，**不要只凭路径臆测**）。据此追溯每处改动对应的需求与设计变更。
- 用户声明的**库/第三方目录**：**跳过**，不对其中的代码做任何变更分析。
- 每条分析结论**记下它来自哪个文件/函数/变更**，供用户核对；**不得臆造**变更项。两版代码冲突或无法判定变更意图时，标出来问用户。

- 通读材料，把结论提炼成一份**结构化清单**，写入 `<项目根>/.agentemployee/gjb438c-ida/change-digest.md`，至少覆盖：
  - 软件识别信息（名称、简称、版本、开发单位等）与变更背景；
  - **需求变更清单**（新增 / 修改 / 删除）：每条的依据、标识号、说明、性能指标、限制与约束；
  - **设计变更清单**：每条的依据、标识号、说明、约束条件；
  - **代码变更清单**：每条的依据、标识号、说明、约束条件；
  - **变更之间的关联**：哪些变更同源、互为连锁或属于同一缺陷的不同表现（据此在阶段二合并为一个变更项）；
  - 每条变更对**关联需求、关联设计、关联编码**的影响；其中**编码影响要落成具体代码位置**（存在新代码的写新代码路径，代码被删除的写老代码路径）；
  - 对**其他关联软硬件**的影响与兼容性结论；
  - 测试验证情况（环境与结论）；
  - **材料中缺失或存疑的点**（明确标出，供用户补充）。

**配图（可选）**：本报告模板未固定配图章节。若用户明确要求补充影响关系图、调用链图等，填充完成后用 `docx-figures` 技能插入；图数据必须来自两版代码对比或用户输入，**不得臆造**。多张图可用 `docx-figures` 的 `--manifest` 一次渲染、一次插入（脚本内置能力，不算自写脚本）。

### 阶段二 · 变更项大纲确认（必须逐条列全，然后停下等待确认）

**这是"第一步"——只出大纲，不写正文。** 基于清单，先把所有变更**归类并合并**，形成变更项大纲，并且**必须显式列出**（不能只说"将生成若干条"）：

- **归类（每项只出现一次）**：逐项判定它属于 3.1 需求变更 / 3.2 设计变更 / 3.3 代码变更中的**哪一类**，只在该类下列出；同一变更**不得**跨章重复出现。大纲里要能看出"某一项属于哪类、为什么"。
- **合并（关联的算一条）**：把能关联到一起的变更（同源连锁改动、同一缺陷的不同表现、成组的新增/修改/删除）合并成**一个变更项**；在大纲中**注明合并了哪些原始变更及合并理由**。
- **3.1 需求变更及其影响域分析**：逐条给出 `3.1.1 <变更名>`、`3.1.2 …`，每条一句话说明变更类型（新增/修改/删除）与要点；每条固定三个子项：`3.1.x.1 对关联需求的影响`、`3.1.x.2 对关联设计的影响`、`3.1.x.3 对关联编码的影响`；
- **3.2 设计变更及其影响域分析**：逐条给出 `3.2.1 <变更名>`…；每条固定两个子项：`3.2.x.1 对关联设计的影响`、`3.2.x.2 对关联编码的影响`；
- **3.3 代码变更及其影响分析**：逐条给出 `3.3.1 <变更名>`…；每条固定一个子项：`3.3.x.1 对关联编码的影响`；
- 第 1 章基本信息（软件标识、概述、变更背景）、第 2 章依据文件、第 3 章变更汇总、第 4～6 章的要点（可概述，但不得留空不提）。
- 每个 `3.x.y` 的正文按 `a)依据 / b)标识号 / c)说明 / d)性能指标 / e)限制与约束` 写（设计/代码变更可省略性能指标一栏，但其余不得留空）。**不再单列「变更描述」子节**——变更本身是什么，写在 `3.x.y` 正文的 a)–e) 字段里。

#### 影响子节写法（固定，不得增减子节）

子节结构由变更类型决定，**不设「变更描述」子节**；「对关联X的影响」按下面的规则写：

| 变更类型 | 子节（按序） | 写什么 |
| -------- | ------------ | ------ |
| **需求变更** `3.1.x` | 1. 对关联需求的影响 | **写「无」**（该变更就是需求变更，不再牵连其他需求条目） |
| | 2. 对关联设计的影响 | **该需求自身对应的设计变化**，写清**变更前 → 变更后** |
| | 3. 对关联编码的影响 | **该需求对应的全部代码位置**（见下方「代码位置写法」） |
| **设计变更** `3.2.x` | 1. 对关联设计的影响 | **写「无」** |
| | 2. 对关联编码的影响 | **该设计对应的全部代码位置**（见下方「代码位置写法」） |
| **代码变更** `3.3.x` | 1. 对关联编码的影响 | **该变更涉及的全部代码位置**（见下方「代码位置写法」） |

**代码位置写法**：直接点出具体位置（文件路径，尽量到函数/符号），**不要**写"相关代码""若干文件"这类笼统话。
- **有当前版本代码的，写新代码位置**（当前版本路径）；
- **代码被删除的，写老代码位置**（变更前路径）。

输出后**停下，等用户确认或修改**（用户可能调整分类与合并）。用户未确认前：不要填写正文、不要建工作副本、不要运行引擎。**大纲一旦确认即冻结——只按大纲生成，不擅自增减或拆并变更项，也不改子节结构。**

## 四、JSON 规则

**config.json**：分 `project`、`document`、`content` 三部分，只修改各字段的 `content` 值，不动 `type`、`replacement_pattern` 等结构字段。本模板封面**只有** `project.name`、`project.short_name`、`project.version`、`project.company`、`document.id`、`document.title`、`document.classification`、`document.phase`、`document.date` 会被写入。

**project.json**：

- 只修改 `content`、`subsections` 与 `rows`；不改 `id`、`name`、`type`、`columns`、`replacement_pattern`、`locator_rows`、`table_id` 等模板结构字段。
- 章节组织（`structure` 的键）：

  | 键   | 章节                     | 填写方式                                                                                                                         |
  | ---- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
  | `1`  | 基本信息                 | `placeholders`：1.1 软件标识 / 1.2 软件概述 / 1.3 变更背景                                                                       |
  | `2`  | 依据文件                 | `content`（一句导语）+ `tables`：依据文件表                                                                                      |
  | `3`  | 变更来源及其影响域分析   | `content`（汇总导语）+ `tables`：变更汇总表 + `placeholders`：动态 `3.1` / `3.2` / `3.3`（各含 `subsections`）                   |
  | `4`  | 对其他关联软硬件的影响   | `content`                                                                                                                        |
  | `5`  | 测试验证情况             | `placeholders`：5.1 测试环境 / 5.2 验证信息                                                                                      |
  | `6`  | 其他事项                 | `content`                                                                                                                        |

- `3.1 / 3.2 / 3.3` 是**动态章节**，作为 `structure["3"].placeholders` 出现（`insertionParentScope: "placeholder"`）。每个动态章节用 `content`（本章导语）+ `subsections` 描述子节。
- `subsections` 的键是有效章节编号（如 `"3.1.1"`、`"3.1.1.1"`）；数字按编号排序，引擎自动加章节号。

### 动态子节（subsections）写法

每个子节是 `{ "name": …, "content": … }`，可**递归**再嵌套 `subsections`：

- `name`：子节标题（引擎自动加章节号，如 `3.1.1 新增转义字符处理需求`，不要自己写编号）。
- `content`：该子节的正文；按 `\n` 拆成多段。无正文可省略，但不得为空。
- `subsections`：更深一层子节（如 `3.1.1` 下的 `3.1.1.1`）。

`3.x.y`（变更项本体）的 `content` 按行照写 a)–e) 字段（引擎只把 `content` 按行复制成段落，**不会**自动加字段名或编号）：

```
a)依据：<该变更的依据>
b)标识号：<变更标识/编号>
c)说明：<变更内容与行为>
d)性能指标：<指标；不适用的写"无">
e)限制与约束：<约束条件>
```
